The problem

A restaurant that runs on memory

Finds out too late

The owner learns paneer ran out when a diner sends back a dish — not when the shelf got low.

Counts at midnight

Which items sold, and whether today was good, is answered hours after anything could be done about it.

Forecasts by feel

Prep quantities come from instinct. Being wrong costs either wasted food or turned-away covers.

A WhatsApp group, a paper KOT pad, and one person holding the whole operation in their head.

Safety

Guardrails are code, not instructions

What we measured

The system prompt told the agent it could not order from suppliers. It agreed — “I have no capability to contact suppliers” — and proposed a restock note anyway.

3 trials out of 3. The eval requires 5 out of 5.

So the capability boundary moved into code and now runs before the model is called. Requests for things this product cannot do never reach it.

A prompt is a strong prior. It is not a guarantee.

Three layers

  • The tool does not exist. Nothing in the registry moves money, discounts, refunds, or contacts a supplier.
  • Out-of-scope requests are refused in code, deterministically, before any model call.
  • The approval gate is server-side. Skipping the UI does not help; re-approving returns 409 so a replay cannot fire twice.

Only the Compliance Nudge Agent acts unapproved — it holds no tools at all and can only notify.

Honesty

The model narrates. It never calculates.

Forecasting is a published formula, computed in TypeScript and printed with its own arithmetic beside it:

forecast_qty = weekday_average × trend_factor trend clamped to ±30% — over a 28-day window one unusual week otherwise tells a kitchen to triple its prep
  • Every AI-surfaced number prints the basis it came from.
  • Asked about a dish never sold, it says it has no records rather than guessing.
  • Sales history is synthetic — and the briefing says so out loud, unprompted.

Architecture

One app, one deploy, one thing that can break

DecisionWhy
Next.js 16 App Router · Supabase · Vercel Single deploy target. Route handlers give server-side enforcement, which the spec requires.
Polling at 2s, not Realtime The cross-surface sync is the core demo moment. It cannot ride on a websocket debugged at 3am.
Server prices every order Prices come from the database, never the request. A sold-out item is refused with a 409, not merely greyed out.
Groq primary, Gemini failover, offline fallback Measured: gemini-3.6-flash free tier is 20 requests/day, not the ~250 assumed. Groq gives 1000. The plan was reversed on evidence.
Every proposal persisted before approval The audit trail records what was suggested even when the owner says no.

Scope

What we cut, and what we would not

Cut, deliberately

  • Google OAuth and the login UI — the role guard is written and tested, one env var turns it on
  • Staff and Customers CRUD
  • Supabase Realtime — polling works and cannot fail
  • Floor-plan visualiser
  • LLM-judge calibration — the least return of any eval layer for the hours it costs

Never on the table

  • Cross-surface live sync
  • One working agent behind an approval gate
  • The Agent Activity Log
  • A briefing grounded in real computed figures
  • A deployed URL and a README

Sales history is synthetic and labelled as such in the database, the API, and the UI. Fabricating “real” trading data would contradict everything else here.
